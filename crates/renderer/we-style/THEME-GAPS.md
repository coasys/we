# Theme parity gap table (round A)

What a WE web theme can change vs. what the egui renderer paints today, per theme.
"Rust status" cites code under `crates/renderer/`; "egui path" is how the gap could close in
round B (egui 0.37). The token _tables_ are already shared — `we-app/src/gallery.rs:26
load_theme_set` loads the same `tokens/<theme>.json` conformance vectors the browser recorded —
so every row below is a _paint/behaviour_ gap, not a missing value.

Legend: **ported** = paints correctly · **partial** = paints something but visibly different ·
**missing** = parsed or retained but nothing reaches the screen.

## Data notes

- `Style::unsupported` retains unevaluated expressions (gradients, `color-mix`, undeclared vars)
  rather than guessing — the honest "paints nothing" signal this table builds on.
- `color-mix`/`oklch(from …)` appear inside recorded values (glow roles, `GLOW_SHADOW`); until
  `we-style/src/color.rs` evaluates them, those tokens stay decorative strings.
- The `we-egui` scrollbar is egui's stock one — even where `--we-scrollbar-*` resolves, nothing
  reads it (`we-style/src/style.rs` `scrollbar_*` fields exist, no consumer).
