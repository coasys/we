# Decision: JSON Schemas as the App Definition Layer

## Status

**Accepted** — foundational architectural decision. All plan documents build on this.

## Context

WE uses a JSON schema system to define app UIs. Schemas reference components by name, bind to data via tokens like `$query` and `$store`, and support iteration (`$forEach`), conditionals (`$if`), routing (`$routes`), and transformations (`$map`, `$pick`, `$filter`, `$find`, `$count`). The system has ~18 operators — an expression language embedded in JSON.

The question is whether this is the right architectural direction, or whether WE should use code-based templates (JSX/TSX), a visual builder, a compiled DSL, or some other approach.

This is the most consequential architectural decision in WE. If it's wrong, everything built on top — the apps ecosystem, MCP tooling, section-level sharing, AI editing — is built on the wrong foundation.

## The Concern

JSON/XML DSLs that grow into programming languages have a rough history. XSLT, BPEL, Salesforce formulas, and SharePoint CAML all started as declarative data formats and became unmaintainable as they accumulated operators. They suffered from: no debugger, no stack traces, no IDE autocomplete, terrible error messages, and manual find-and-replace refactoring.

If WE's schema system follows this trajectory, we'd end up with an unmaintainable custom language embedded in JSON — the worst of both worlds.

## Why the XSLT Comparison Is Misleading

Those systems failed for a specific reason: **they tried to replace general-purpose programming.** They became Turing-complete, had loops and recursion and string manipulation and error handling, and humans had to write and maintain them by hand. That combination is genuinely terrible.

WE's schema system is architecturally different in three ways:

### 1. Deliberately non-Turing-complete

No loops, no recursion, no variables, no general computation. `$expr` (arbitrary JS via `new Function()`) was specifically identified and removed. The operators are declarative bindings (connect data to UI), not imperative instructions (do X then Y). They're closer to HTML attributes than to a programming language.

### 2. The component escape hatch prevents language bloat

When something is genuinely complex (audio playback, drag reordering, rich text editing), it becomes a framework component (currently SolidJS) — NOT a new operator. This is what XSLT lacked. XSLT kept adding to the language because there was no escape. WE's schema says "I can't express this" and delegates to code.

The gating principle ("new tokens require 3+ real templates AND can't be done with existing tokens") is the formal rule that prevents the XSLT trajectory. The moment you'd add a new operator to avoid writing a custom component, you're on the wrong path. The escape hatch to real code must remain the preferred path for complex behavior.

This is the single most important defence in the design. See the dedicated section below.

### 3. AI is the primary author, not humans

This genuinely changes the calculus. The historical complaint about JSON DSLs is that humans can't read, write, or debug them. If the primary interaction is "tell AI what you want → AI generates JSON → system validates and renders," human readability is secondary. The format optimizes for machine generation and consumption, which JSON is ideal for.

Note: the claim that LLMs are better at generating JSON than TypeScript/JSX has weakened as models improved. The stronger current argument is the **MCP validate loop**: schemas have a finite, validatable grammar that catches errors programmatically before render. Arbitrary SolidJS can fail silently at runtime in ways that are much harder to detect statically. The structured output is valuable primarily because it is _checkable_, not just because it is simpler to generate.

## Industry Precedent: Server-Driven UI

WE's approach is not without precedent. Airbnb, DoorDash, Lyft, and other large-scale mobile apps independently converged on **Server-Driven UI (SDUI)**: the server sends a JSON description of the screen; the client renders it. They arrived at this architecture for exactly the same reasons — decoupled iteration, centralised control, renderer flexibility — and it works at massive scale.

The differences that make WE's version go further:

- SDUI is **trusted**: server and client are controlled by the same company. WE must handle schemas from strangers.
- SDUI is **not remixable**: the server sends whole screens. WE needs section-level composition.
- SDUI predates **AI authoring**: the JSON is generated by server code, not by an LLM instructed by a user.

SDUI validates the core idea. WE extends it to the decentralized, community-authored, AI-first case — which requires stronger guarantees and different design choices, but the foundational premise is proven.

## Why JSON Schemas Are Specifically Right for WE

WE has three constraints that together make JSON schemas almost the only viable choice:

### Constraint 1: Section-level remixability requires transparency

You can't share "part of a React component." Components are opaque — you can compose them but not decompose them. JSON schemas are transparent — you can extract a route section, a sidebar section, a theme section. You can splice sections from different templates into your own layout. You can diff two schemas and surgically apply one community's nav style to another community's content layout.

This is one of WE's most compelling features and it _only works_ because schemas are data, not code. This property is **independent of sandboxing technology** — even with a future capability-limited WASM component standard, a compiled artifact is still opaque. You can compose at its boundary but not decompose below it. The data/code distinction is what makes remixability possible, not the security model.

### Constraint 2: Decentralized template sharing requires safety

Templates are received from strangers via AD4M. Whatever format they use must be **safe to receive and render without trust.** JSON is inert — it can't execute code, access cookies, or phone home. A React component can. A SolidJS file can. An ESM bundle can. JSON can't.

This is a strong current constraint. If capability-limited sandboxing (e.g. WASM components) matures, this constraint relaxes — but remixability (Constraint 1) doesn't. The architecture doesn't depend on sandboxing remaining hard.

### Constraint 3: AI as the primary builder requires structured, validatable output

JSON has a fixed grammar and schemas have a validatable structure. The MCP → validate loop can catch errors _before rendering_ and feed them back to the model for correction. This structured error-correction cycle is hard to replicate with arbitrary TypeScript/JSX, where failures surface at runtime in ways that require human debugging.

Generating valid SolidJS requires understanding reactivity, lifecycle, imports, and the full JavaScript language surface. Generating a valid schema requires knowing ~18 operators and a component list — a much smaller and more enumerable surface.

## Alternatives Considered

| Approach                            | Safe to share?      | Section-remixable?          | AI-friendly?                    | Full expressiveness?     |
| ----------------------------------- | ------------------- | --------------------------- | ------------------------------- | ------------------------ |
| **JSON schemas + component escape** | ✅ Inert data       | ✅ Sections are JSON chunks | ✅ Structured, validatable      | ✅ Via custom components |
| Code templates (JSX/TSX)            | ❌ Arbitrary code   | ❌ Opaque                   | ⚠️ Harder to generate correctly | ✅ Full language         |
| Visual builder (Webflow-style)      | ✅ State, not code  | ⚠️ Possible but complex     | ❌ AI can't "click buttons"     | ⚠️ Limited logic         |
| Compiled DSL (Svelte-style)         | ❌ Compiles to code | ⚠️ Pre-compilation only     | ⚠️ Custom syntax                | ✅ Full language         |
| Web Components as sharing format    | ❌ JS bundles       | ❌ Opaque                   | ⚠️ Harder                       | ✅ Full language         |
| MDX (Markdown + components)         | ⚠️ Can embed code   | ⚠️ Text-level only          | ⚠️ Unstructured                 | ⚠️ Limited logic         |

Nothing else hits all three constraints. Code-based approaches sacrifice remixability and safety. Visual builders sacrifice AI authoring. Compiled DSLs require tooling investment comparable to building a language. JSON schemas with a component escape hatch are the Pareto-optimal point for WE's specific requirements.

## The Component Escape Hatch: The Defence Against DSL Bloat

This deserves its own section because it is the single mechanism that prevents WE's schema system from following the XSLT trajectory.

The rule: **when behaviour is too complex to express cleanly in schema tokens, it becomes a framework component — not a new token.**

XSLT failed because it had no escape. Any new requirement had to become part of the language. WE's schema can always say "I can't express this" and hand off to a first-class component. The schema is a _description_ of the UI; the component library is the _implementation_ of the UI. This boundary is not incidental — it's structural.

Signs the escape hatch is being used correctly:

- A new token replaces imperative store code that was doing data joins or aggregation (e.g. `$filter`/`$count`/`$find` replacing `loadEntitySignalData`)
- The token has an obvious mental model matching an existing programming concept (filter, count, find)
- At least 3 real templates need it independently

Signs the escape hatch is being violated:

- A token is added to avoid writing a custom component
- The token is specific to one use case
- The token requires imperative-style sequencing or side effects

The gating principle must hold: "New tokens require demonstrated need across 3+ real templates, AND cannot be reasonably expressed with existing tokens."

## Load-Bearing Dependencies

The schema system's viability depends on three supports that must all be solid:

### 1. Component library coverage

The core library must be comprehensive enough that schemas handle 80%+ of UI needs without custom components. If users constantly need custom components, the schema becomes boilerplate glue rather than the primary app definition. This is the highest practical risk.

### 2. AI tooling pipeline

If AI is the primary schema author, the quality of AI output determines the entire system's viability. The `@we/ai-context` package (which generates the component catalogue, token reference, and schema examples fed to the model) together with the MCP → validate loop form **load-bearing infrastructure**. If it's flaky or incomplete, users are stuck hand-editing JSON with ~18 operators and no tooling — which is exactly the XSLT failure mode.

### 3. Token set boundary discipline

See the component escape hatch section above. The escape hatch to framework components is the defence against DSL bloat. Complex behaviour should become components, not operators.

## Framework Agnosticism: A Structural Property, Not a Goal

The schema system contains no framework-specific primitives. `$query`, `$store`, `$local`, `$if`, `$each`, and all other tokens are abstract — they describe _what_ to render and _what data to bind_, with no assumptions about _how_. This is not by coincidence; it's a consequence of schemas being data rather than code.

The monorepo is structured to support this explicitly:

- **`packages/schema-system`** — pure TypeScript, no framework dependency. Token types, Zod validators, and `resolveProp` are already renderer-agnostic.
- **`packages/design-system`** — each component directory contains per-framework implementation files (e.g. `MyComponent.solid.ts`, `MyComponent.react.ts`). Adding a new framework means adding co-located implementation files alongside the existing ones, keeping all variants of a component together.
- **`packages/app-shell/src/frameworks/`** — the renderer itself, one per framework. Today only `solid/` exists.

Adding a React or Vue renderer requires:

1. A renderer tree-walk that maps schema nodes to framework component instances (moderate work, same pattern as the SolidJS renderer)
2. Per-framework implementation files for each design-system component (mechanical work — the primitives layer is already framework-agnostic, and components are kept intentionally pure, making AI-assisted generation of matching implementations for other frameworks highly viable)

No changes to the schema, token system, or any existing templates. **A template authored today works in any future renderer without modification.** This means templates survive framework migrations and can target native mobile renderers, spatial UI runtimes, or anything else that can walk a JSON tree.

This also strengthens the long-term case for the architecture: even if SolidJS falls out of favour, the schema layer doesn't. The investment in templates is durable in a way that framework-coupled code is not.

## Decision

JSON schemas with a component escape hatch are the right architecture for WE. The approach uniquely satisfies WE's three constraints (section-level remixability, decentralized sharing safety, AI-first authoring) that no alternative approach handles simultaneously.

Critically, the two most fundamental properties — remixability and framework agnosticism — are consequences of schemas being _data_, not consequences of the security model. They survive any future advances in sandboxing technology. The architecture is not a temporary workaround; it is the right abstraction level for the problem.

The architecture is sound. The execution risks — component library coverage, AI tooling reliability, and token boundary discipline — are real but addressable, and are specifically targeted by the PR roadmap.
